# Nix Capsules 18: Store Internals

## Introduction

In the previous capsule, we learned how dependencies propagate through the build graph. Now, we will look at **Store Internals**—specifically, how Nix calculates those cryptographic hashes in `/nix/store/...` and how it proves that your builds are truly reproducible.

Understanding this will give you the power to debug caching issues and figure out exactly *why* a massive library is secretly sneaking into your lightweight application.

## The Hash Trap (Fail-First)

Nix is an **Input-Addressed** system. This means the hash of a build output (e.g., `/nix/store/123...-my-app`) is calculated from its inputs (the source code, the compiler, the build script).

But there is a catch: **What if the input is a download from the internet?** Nix cannot know the hash of a file on a remote server until it downloads it. If the server secretly changes the file tomorrow, your build would change, breaking reproducibility!

Let's see how Nix handles this.

**File:** `flake.nix`

```nix
{
  description = "Store Internals Demo";
  inputs.nixpkgs.url = "github:nixos/nixpkgs/nixos-unstable";

  outputs = { self, nixpkgs }: let
    system = "x86_64-linux";
    pkgs = nixpkgs.legacyPackages.${system};
  in {
    packages.${system} = rec {

      # 1. THE DOWNLOAD (Fixed-Output Derivation)
      # We use fetchurl directly. This creates an FOD.
      my-download = pkgs.fetchurl {
        url = "https://raw.githubusercontent.com/NixOS/nix/master/README.md";
        
        # ⚠️ THE TRAP: We provide a completely wrong hash
        sha256 = "sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=";
      };
      
      default = my-download;
    };
  };
}
```

**Try to build it:**

```bash
git init && git add flake.nix
nix build .

```

**The Failure:**
Nix will download the file, hash it, and then scream at you:
`error: hash mismatch in fixed-output derivation '/nix/store/...-README.md.drv'`
`specified: sha256-AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA=`
`got:       sha256-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx=`

## Step 1: Fixed-Output Derivations (FODs)

To fix the error, copy the `got:` hash from your terminal and replace the `sha256-AAAA...` string in your `flake.nix`.

Run `nix build .` again. It will succeed!

**The Glass Box:** What just happened?
When you use fetchers like `fetchurl`, you create a **Fixed-Output Derivation (FOD)**.
Unlike standard builds, Nix says: *"I don't care about the inputs (the URL). I only care about the final content."* The store path for `my-download` is calculated **exclusively from the hash you promised**.

**The "Link Rot" Test:**

1. Change the `url` in your flake to some other valid mirror of that file. (`https://raw.githubusercontent.com/NixOS/nix/refs/heads/master/README.md`)
2. Keep the `sha256` exactly the same.
3. Run `nix build .`.
Nix won't even try to download it again! Because the requested hash matches a file already in your `/nix/store`, the output path remains identical. This is how Nix safely interacts with the impure, ever-changing internet.

## Step 2: Input vs. Content Addressing

Now we can define the two core paradigms of the Nix Store:

1. **Input-Addressed (Standard Builds):** The store path is generated by hashing the `.drv` file (the instructions). If you change `gcc` from v12 to v13, the input changes, so the output path changes.
2. **Fixed-Output (Downloads):** The store path is generated by hashing the *promised content*. Used strictly for bridging external data into the pure Nix store.

> **Didactic Check:** If I change the `name` attribute of an Input-Addressed derivation, will it rebuild?
> *Yes!* The `name` is part of the `.drv` inputs. Changing it alters the input hash, resulting in a new store path.

## Step 3: Inspecting Runtime References

Once a package is in the store, how does Nix know what to keep during Garbage Collection? It scans the binary outputs for exact `/nix/store/...` strings.

Let's add an application that consumes our FOD to see this in action. Update your `packages` block:

```nix
    packages.${system} = rec {
      
      my-download = pkgs.fetchurl {
        url = "https://raw.githubusercontent.com/NixOS/nix/master/README.md";
        sha256 = "sha256-xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx="; # Use your real hash
      };

      # 2. THE APP (Input-Addressed Derivation)
      my-app = pkgs.stdenv.mkDerivation {
        name = "my-app";
        dontUnpack = true;
        
        # We use the 'cowsay' tool to read our downloaded file
        buildInputs = [ pkgs.cowsay ];
        
        installPhase = ''
          mkdir -p $out/bin
          # We hardcode the path to 'cowsay' and 'my-download' in our script
          echo "#!${pkgs.bash}/bin/bash" > $out/bin/my-app
          echo "${pkgs.cowsay}/bin/cowsay -f tux < ${my-download}" >> $out/bin/my-app
          chmod +x $out/bin/my-app
        '';
      };

      default = my-app;
    };
```

Build it and run it:

```bash
nix run .
```

Now, let's peek inside the database. What does `my-app` physically depend on to run?

```bash
nix path-info --recursive --size --human-readable ./result
```

You will see the **Closure** (everything needed to run the app), including `bash`, `cowsay`, your `my-download` text file, and `glibc`.

## Step 4: The Detective Tool (`why-depends`)

In large projects, you might run `nix path-info` and see massive packages like `python3` or `rustc` in your runtime closure when you only wrote a simple Bash script.

To debug *why* a specific dependency is dragging down your closure size, we use `nix why-depends`.

Let's ask Nix exactly how `cowsay` ended up in our `my-app` closure:

```bash
nix why-depends .#my-app /nix/store/dzi68gvj7y25iidp3lyha6cwzi3rgqwr-cowsay-3.8.4
```

**The Output:**

```text
/nix/store/fw4brz3ngfnmhawbpibwdarcxya68sz1-my-app
└───/nix/store/dzi68gvj7y25iidp3lyha6cwzi3rgqwr-cowsay-3.8.4
```

**The Glass Box:** `why-depends` scans the bytes inside the output files and prints which store paths it found and in which file. Nix literally relies on string-matching to build the runtime dependency graph.

## Summary

* **Input-Addressed:** Normal derivations. The store path changes if the build instructions or inputs change.
* **Fixed-Output (FOD):** Downloads. The store path is derived purely from the `sha256` hash you promise.
* **Hash Mismatch:** Occurs when an FOD downloads a file whose actual hash doesn't match your promise.
* **References:** Nix discovers runtime dependencies by scanning the output files for `/nix/store/...` strings.
* **Debugging:** Use `nix why-depends <target> <dependency>` to find exactly which file is holding onto a bloated dependency.
